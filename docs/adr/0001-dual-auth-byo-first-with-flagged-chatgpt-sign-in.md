# ADR 0001: 認証は両対応とし、BYO API キーを先行して出荷する

## Status

- Accepted

## Decision Drivers

- ChatGPT の有料プランを契約している利用者に、追加の API キー管理をさせたくない
- API キーを用意できる利用者と、OpenAI 互換の別提供元を使いたい利用者を同時に支えたい
- Sign in with ChatGPT（SIWC）のモバイル向け仕様と提供条件は変わりうるため、出荷をそれに依存させない
- 認証の失敗が解析や書き出しの実装へ波及しないよう、境界を一つに保ちたい

## Context

tansu は名刺画像の解析に言語モデルを使う。接続先は二種類ありうる。

1. ChatGPT のプラン契約に紐づく認証（SIWC）
2. 利用者が用意した API キーと、任意の OpenAI 互換 API の base URL（BYO）

SIWC はプラン契約者にとって課金と鍵管理の負担が小さい。一方で、モバイルアプリからの利用可否、同意画面、トークンの寿命、API の形は OpenAI 側の都合で変わる。BYO は仕様が安定しており、互換 API を含めていま実装できる。

初期リリースで両方を同時に完成させると、SIWC の不確実性がアプリ全体の出荷を止める。

## Options Considered

- BYO のみ: 実装と検証が単純だが、プラン契約者の鍵管理負担が残る
- SIWC のみ: 体験は良いが、提供条件の変更でアプリが動かなくなる危険が大きい
- 両対応を同時に出荷: 認証経路が二つとも未検証のまま公開される
- 両対応を設計し、BYO を先行して出荷し、SIWC を機能フラグで隔離する

## Decision

- 認証は「解析リクエストに使う資格情報と接続先を返す」一つのインターフェースにまとめる。解析側は SIWC と BYO を区別しない
- BYO API キーを先に実装・出荷する。base URL を設定可能にし、OpenAI 互換 API を受け入れる
- SIWC は実装を別モジュールに置き、機能フラグで有効化する。フラグが無効なビルドでは SIWC の画面・通信・依存を利用者に見せない
- API キーは Android Keystore で保護した領域に保存し、平文で Preferences やログへ出さない
- SIWC の仕様変更は SIWC モジュール内で吸収し、BYO の経路を変更しない

## Consequences

- Positive: SIWC の不確実性があっても BYO で出荷できる
- Positive: 解析コードは接続方式を知らず、テストでは偽の認証実装を差し込める
- Negative: 認証経路が二つあるため、設定画面と失敗時の案内をそれぞれ用意する必要がある
- Negative: SIWC の機能フラグを外すまで、無効な経路のコードとテストを維持する
- Follow-up: SIWC を既定にする場合は、提供条件とモバイル対応を確認した新しい ADR でフラグの扱いを決める

## Adoption and Exceptions

- 解析・書き出しのコードから SIWC 固有の型やトークン形式を参照しない
- SIWC を有効にする変更は、機能フラグの既定値と同意画面の文言を同じ変更で更新する
- 新しい認証方式は既存インターフェースの実装として追加し、解析側の分岐を増やさない
